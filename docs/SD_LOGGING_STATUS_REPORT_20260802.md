# CoreS3 microSD ログ不具合 詳細報告

作成日: 2026-08-02  
対象: `m5stack-cores3-telemetry-bridge`（M5Stack CoreS3）

## 結論

現時点で、CoreS3 のmicroSDログは**安定運用可能とは判定できない**。

SD SPIクロックを25 MHzから10 MHzへ下げ、カードのフォーマットも実施した。しかし、フォーマット直後の10秒ログは成功した一方、次の60秒ログは411レコードで失敗した。失敗時はSDカードへの書込みコマンドが応答しなくなり、ログは途中停止する。

このため、原因はSPI速度だけでも、ファイルシステムの破損だけでもない。最優先の次試験は、**別のmicroSDカードを用いた同一60秒試験**である。これによりカード自体と、CoreS3側のカードソケット・3.3 V電源・SPI信号品質を切り分ける。

## 現在の実機・ファームウェア状態

| 項目 | 状態 |
| --- | --- |
| CoreS3 | 接続確認済み。USBシリアル: COM6、MAC: `30:ed:a0:d4:bf:40` |
| 制御側XIAO ESP32S3 | 接続確認済み。USBシリアル: COM4 |
| CoreS3ファームウェア | `m5stack-cores3-telemetry-bridge` の10 MHz SD SPI版を書込み済み |
| SD初期化 | `SD.begin(kSdCsPin, SPI, 10000000)`。以前の25 MHzから変更 |
| UART | 921600 bps、Core GPIO8=RX / GPIO9=TX。今回の切り分け中は変更していない |
| ESKF・センサ設定・ログ形式 | 今回のSD切り分け中は変更していない |
| SoftAP | SSID `BOAT-ESKF-CORE`、パスワード `12345678`、Core IP `192.168.4.1` |
| ビルド | 成功。RAM 145,452 / 327,680 bytes、Flash 1,015,721 / 6,553,600 bytes |

CoreS3への書込みは通常のPlatformIOアップロードではなく、安定確認済みのESP-ROM `--no-stub`方式を使用した。全イメージのhash verifiedを確認済みである。

## ログ処理の構成

1. 制御側XIAOからCoreS3へUARTでフレームを受信する。
2. CoreS3は受信フレームをリングキューへ格納する。
3. `SdWriter`タスクがキューから取り出し、SDへBIN形式で書込む。
4. 正常停止時にはBINをflush/closeし、同名のTXT要約を生成する。

過去に`SdWriter`の4 KBスタックでstack canary panicが発生したため、スタックを12 KBに増量し、優先度を1、ループ末尾に1 ms待機を入れた。このタスクスタック不足は解消している。今回の問題はpanicではなく、SDカードがSPIコマンドへ応答しなくなる問題である。

## 実測の時系列

| 試験 | 条件 | 結果 |
| --- | --- | --- |
| RUN0001〜RUN0003 | 初期の通常ログ | RUN0001/2/3には有効なログ実績あり。RUN0003は60秒正常ログ |
| RUN0004〜RUN0010 | 4 KB `SdWriter`時 | stack canary panic。0 byteログが発生 |
| RUN0011 | 12 KB化後の10秒試験 | 208,556 byteとTXTを正常作成。ログ処理タスク修正の有効性を確認 |
| RUN0012〜RUN0014 | 25 MHz、カード抜き差し後を含む | CMD18/CMD0D/CMD00失敗。書込み途中で停止 |
| RUN0016 | 10 MHz | 65レコードでCMD18、その後CMD0D/CMD00。速度低下では解消せず |
| フォーマット後10秒 | 10 MHz、同カード | 1,719レコードまで到達し、自動停止。SDコマンド失敗なし |
| フォーマット後60秒 | 10 MHz、静止状態 | 411レコードでCMD18、その後CMD0D/CMD00。60秒を完走できず |

## 60秒試験の直接証拠

60秒試験は `POST /api/log/start?duration_s=60` に対しHTTP 202で開始された。直後は正常にレコード数が増加した。

| 観測値 | 内容 |
| --- | --- |
| `rec=157` | 書込み開始後も動作していた |
| `rec=342` | 継続して書込みできていた |
| `rec=411` | 直後にSD通信が失敗し、以後停止 |
| `log=0`, `q=0`, `rec=411` | ログ停止後、キューは残らず、60秒完走ではない |

発生した診断は次の通り。

```text
sdCommand(): Card Failed! cmd: 0x18
sdCommand(): Card Failed! cmd: 0x0d
ff_sd_status(): Check status failed
sdCommand(): Card Failed! cmd: 0x00
VFSFileImpl(): fopen(/sd/BOATLOG/RUN0002.TXT) failed
```

CMD18は複数ブロック読出し、CMD0DはSD状態取得、CMD00はカードをアイドル状態へ戻すコマンドである。書込み中にカードとのSPI通信が崩れた後、状態確認・終了処理・TXT要約作成まで連鎖して失敗している。UARTやESKFのエラーではない。

## 現時点で除外・未除外の原因

| 仮説 | 判定 | 根拠 |
| --- | --- | --- |
| `SdWriter`タスクのスタック不足 | 主因から除外 | 12 KB化後はstack canary panicが出ない。今回の失敗はSDカードコマンド失敗 |
| UART受信停止 | 主因から除外 | SD失敗後もUARTのbytes/framesは増加している |
| ESKFやBNO08X処理 | 主因から除外 | 変更しておらず、エラー発生箇所は`sd_diskio.cpp` |
| 25 MHzが速すぎる | 単独原因から除外 | 10 MHzでも同じCMD18/CMD0D/CMD00を再現 |
| ファイルシステム状態 | 部分的に関与の可能性 | フォーマット後10秒は成功。ただし60秒持続試験は失敗 |
| microSDカード自体 | 未判定・優先確認対象 | 書込みが間欠的に失敗する。別カード試験が未実施 |
| カードソケット接点 | 未判定 | 抜き差し・フォーマットでも再発。接点不良の可能性あり |
| 3.3 V電源の瞬低・ノイズ | 未判定 | 書込み負荷中にだけ失敗するため候補 |
| SPI配線・信号品質 | 未判定 | 10 MHzでも失敗するため候補 |

## 重要な注意点

- 「フォーマット後の10秒成功」は恒久解決を意味しない。60秒試験が失敗したため、ログ機能は未合格である。
- SD失敗後もCoreS3本体とUART通信は動作を続ける。失敗しているのはSDへの持続書込みである。
- Web APIは起動直後の最初のリクエストは応答する一方、後続の`/api/log/files`等がタイムアウトする既知の不安定さがある。このため今回の判定はHTTP一覧ではなく、CoreS3シリアル診断を一次証拠としている。
- 制御出力は本試験中も有効化していない。ESKFはshadow-onlyであり、VESC・PCA9685を駆動していない。

## 次に行うべき作業

優先順位は以下の通り。

1. **別のmicroSDカードを用意し、FAT32でフォーマットしてCoreS3へ挿入する。**
2. CoreS3を再起動してSDを再初期化する。
3. 同じSD SPI 10 MHz版のまま、静止60秒ログを実施する。
4. CMD18/CMD0D/CMD00が出ないこと、60秒完走、BINとTXT要約の取得を確認する。

別カードで60秒が通る場合、元カードの劣化・互換性・内部状態が主因と判断できる。別カードでも同じ失敗なら、CoreS3のカードソケット接点、3.3 V電源、SPI信号品質の順にハードウェア検査へ進む。
