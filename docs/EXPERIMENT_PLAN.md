# 実機統合計測計画

最終更新: 2026-07-23

## 目的と原則

制御側 XIAO と通信・記録側 XIAO の計測系を、実アクチュエータを動かさない `DRY_RUN` で評価する。目的は、将来の制御周期を決めるための実測根拠を得ることであり、性能を推測で合格扱いにしないことである。

- 1 RUN で変える条件は1つだけにする。I2C速度、ToF設定、INA設定、UART負荷を途中で切り替えない。
- 周辺I2Cは通常運用では400 kHz固定、BNO08X専用I2Cは100 kHz固定とする。
- I2C 100 kHz比較は、100 kHz固定で起動した別RUNとして実施する。100 kHzから400 kHzへの動的復帰試験は通常の性能比較から除外する。
- 各RUNは両XIAOを同じGitコミットでビルド・書込みしてから始める。診断コードは現在 `origin/agent/benchmark-stability` にあり、`main` には未統合である。
- 全RUNで `kDryRunActuators=true` を維持する。VESC非ゼロDuty、サーボパルス、ARM/START操作は許可しない。

## 共通の事前条件

1. 制御側・通信側を同一の診断コミット（現時点では `16de6d6` 以降）でビルドする。
2. 両方を実機へ書込み、コミットID・ファームウェア版・配線・SDカード・ケーブル長を記録する。
3. 通信側のSoftAPとWeb UI、SD認識、GNSS受信、比較BNO、制御側Heartbeat、STOP/E-STOP ACKを確認する。
4. ベンチ開始前に制御側が `DISARMED`、`DRY_RUN=1`、PCA9685全OFF、VESC Duty 0であることを確認する。
5. 各RUNでBIN、TXT、通信側/制御側のシリアルログを同じRUN番号で回収する。

## 全RUNに適用する必須判定

次のいずれかを満たさなければ、そのRUNは性能比較に使わず、原因を切り分けて再試験する。

| 区分 | 合格条件 |
| --- | --- |
| 安全 | `DRY_RUN=1`、開始前後ともVESC Duty 0、PCA9685全OFF、STOP/E-STOP ACKが受理される |
| SD | `normal_stop=1`、`sd_write_errors=0`、`queue_drops=0`、`log_fault=none`、BINを末尾まで復号できる |
| UART | COBS/CRC/長さエラー0、送信キュードロップ0、安定区間のGNSS_NAVとGNSS_PROCESS_RESULTの対応欠落0 |
| 制御側 | 試験中の予期しないリブート、FAULT、BNO/ToF/INA再初期化が0 |
| メモリ | RUN開始時から最小空きヒープの低下が5%未満。3回反復で一方向に低下し続けない |

GNSSの安定区間は、両ノードのHeartbeatが正常になってから5秒後から、停止操作の1秒前までとする。起動・停止境界は欠落判定から除外する。

## 実施順序

| ID | 実験 | 固定条件と変更する条件 | 何を確認するか | 合格後の判断 |
| --- | --- | --- | --- | --- |
| P0 | 診断版の成立確認 | 両XIAOを同一診断コミット、周辺I2C 400 kHz、標準ToF、UART追加負荷なし | ビルド、書込み、Web UI、SD、GNSS、Heartbeat、STOP/E-STOP、ログ回収の経路 | 以降の比較RUNに進む。満たさなければ比較を始めない |
| P1 | 400 kHz基準RUN | 周辺I2C 400 kHz固定、ToF 8×8/10 Hz要求、INA標準、UART追加負荷なし。10分、3回 | 全センサの実測Hz・最大間隔、I2C時間、UART往復、SD完全性、ヒープ | 400 kHzの再現可能な基準値を確定する |
| P2 | I2C速度比較 | P1と同じ構成で周辺I2Cだけ100 kHz固定。電源再投入またはリセット後に開始。10分、3回 | 100 kHzが初期化・保存・GNSS往復を壊さないか、P1に対するToF/INA/I2C時間の変化 | 低速配線が必要な場合に100 kHzを採用できるか判断する。通常値は400 kHzを維持 |
| P3 | ToF設定比較 | I2C 400 kHz固定。8×8/10、8×8/15、4×4/15、4×4/30を各別RUNで5分、各3回 | 実測ToF Hz、最大間隔、欠損、最大読取り時間、他センサ/UARTへの影響 | 実測Hzが要求値の90%以上かつ最大間隔が要求周期の2倍未満の設定だけを後段候補にする |
| P4 | INA設定比較 | I2C 400 kHz固定、標準ToF、UART追加負荷なし。INA current/balanced/fastを各別RUNで5分、各3回 | INA新規値率、重複、I2C時間、ToFとGNSS往復への影響 | 他の必須判定を崩さず、必要なINA更新周期を満たす最小負荷設定を選ぶ |
| P5 | UART負荷比較 | I2C 400 kHz、標準ToF・選定INA。追加負荷0/250/500/630 Hzを各別RUNで5分、各3回 | UART CRC/COBS/長さエラー、キュー、GNSS往復、SD、センサ最大間隔 | 完全性を保てる最大の連続UART負荷を決める |
| P6 | 選定構成の統合RUN | P1〜P5で選んだ設定を固定。10分、3回 | すべての必須判定、結果の再現性、各センサの実測分布 | 受動統合計測の構成を確定する |
| P7 | 長時間安定性RUN | P6と同一固定構成。30分、1回以上 | SD書込み遅延、キュー高水位、ヒープ傾向、再初期化、GNSS/UART完全性 | サーボ/VESCを含む次段階へ進む可否を判断する |

## 判定の扱い

- P1/P2は速度の優劣を決めるための比較であり、100 kHzの数値が低いこと自体は故障を意味しない。必須判定を満たすかと、必要な実測周期を満たすかを分けて評価する。
- P3の要求Hzを満たさない設定は、故障と断定せず「将来の制御周期の根拠に使えない設定」と扱う。
- P4/P5で一つでも必須判定を破った設定は、統合RUNの候補から除外する。
- P6/P7が完了するまで、サーボ出力、VESC 3%、閉ループ制御、航法へ進まない。

## RUN0001から得た初期知見

`D:\BENCH\RUN0001`（`0.2.1-sd-diagnostics`、約10 cm直接配線）は、SD書込みエラー0・キュードロップ0でフェーズ0〜8を完了した。一方、100 kHz試験後に400 kHzへ戻すフェーズで`BenchmarkReady`が届かず`prepare_timeout`となった。このため、動的速度復帰は通常の比較RUNから除外し、P2では起動時から速度を固定する。
